## 0. 판단 기준 (모든 채택/제외 결정의 공통 근거)

1. **데이터 형태 불일치 배제**: KOSHA MSDS 수집물은 API의 EAV(JSON, `msdsItemNameKor`/`itemDetail`/`lev`/`ordrIdx`) 구조다. PDF 원문이 아니다. PDF 파싱을 전제로 한 도구는 원천적으로 대상에서 제외한다.
2. **기존 자산 재사용 우선**: bge-m3, FAISS, 하이브리드 검색(BM25+dense)은 KDIC 프로젝트에서 이미 검증된 자산이다. 신규 모델/스택 도입은 "재사용으로 안 되는 이유"가 명확할 때만 검토한다.
3. **비협상 원칙 우선순위**: 양립성 매트릭스 단독판정 금지, CAMEO 68그룹 체계 엄격 적용, Abstain 정책, 근거등급제(법령>권고>참고) — 어떤 기술 선택도 이 네 가지를 침해하면 안 된다.
4. **검증 가능성**: 문서3에서 제시된 10개 출처는 2026-08-06 기준 claude-in-chrome + Google 검색 스니펫으로 실존/주제 일치를 교차검증했다. 존재는 확인됐으나 세부 수치(예: "72% 향상")는 원문 전체 열람 없이는 미검증 상태임을 전제로 판단했다.

## 1. 채택 항목 (5건)

### 1.1 마크다운 헤더 구조 원칙
- **출처**: hoft.tistory.com/entry/RAG-ext-doc (2026-03-20)
- **무엇을 도입했나**: RAG 최적 포맷은 마크다운(.md)이며, 헤더 계층을 명확히 하고 대명사 사용을 최소화한다는 문서 작성 원칙.
- **왜 도입했나**: EAV의 `lev`/`ordrIdx`는 이미 계층 구조(섹션>항목>하위항목)를 담고 있다. 이 계층을 그대로 마크다운 헤더(`#`/`##`/`###`)로 매핑하면 별도 구조 추론 로직 없이 원본 구조를 보존할 수 있다.
- **도입하면 좋은 점**: (1) 헤더 계층이 곧 청킹 경계가 되어 후속 청킹 로직이 단순해짐 (2) "이 물질" 같은 대명사 대신 화학물질명/CAS를 반복 명시하면 청크 단위로 잘려도 검색 정확도가 유지됨 (3) 사람이 읽어도 검증하기 쉬움(디버깅 비용 감소).
- **예상 단점**: 원문 EAV 항목명이 짧고 반복적인 경우(예: "인화점", "비중") 마크다운 헤더만으로는 어떤 물질의 항목인지 구분이 안 될 수 있음.
- **단점 극복 방안**: 헤더 텍스트 자체에 화학물질명/CAS를 접두어로 강제 포함(`## [에탄올, CAS 64-17-5] 인화점`). 청크가 문서에서 분리돼도 자기완결적으로 식별 가능하게 함.

### 1.2 청킹 토큰 가이드 (기술문서 600~1200자 + 오버랩 10~25%)
- **출처**: tech.ktcloud.com/entry/2025-11-ktcloud-rag-ai-청킹전략-최적화 (2025-11-25)
- **무엇을 도입했나**: 기술 문서 기준 600~1200 토큰, 오버랩 10~25% 권장치.
- **왜 도입했나**: MSDS 항목(예: 섹션10 안정성/반응성 서술형 텍스트)은 EAV 항목 경계만으로는 너무 길거나 짧을 수 있다. 1차 경계는 EAV 항목, 항목이 토큰 상한을 넘는 경우에만 2차로 이 수치를 적용하는 보조 규칙으로 채택.
- **도입하면 좋은 점**: 항목 단위 청킹만으로는 발생하는 "청크 과대/과소" 문제를 보완. 오버랩으로 문장 경계 절단 시 문맥 손실을 줄임.
- **예상 단점**: 오버랩 설정이 과하면 동일 정보가 여러 청크에 중복 임베딩되어 벡터스토어 용량과 검색 노이즈가 늘어남.
- **단점 극복 방안**: 2차 분할은 EAV 항목이 상한을 초과할 때만 조건부 적용(전체 문서 일괄 적용 금지). 오버랩은 권장치 하단(10%)부터 시작해 RAGAS 검증 결과 보고 상향 조정.

### 1.3 하이브리드 검색 (BM25 + Dense)
- **출처**: s-core.co.kr/insight/view/더-정확하고-유연하게-찾는-하이브리드-검색 (2025-06-18)
- **무엇을 도입했나**: 어휘 검색(BM25)과 의미 검색(dense vector)을 결합하는 하이브리드 검색 방식.
- **왜 도입했나**: 이미 KDIC 프로젝트에서 검증된 패턴이라 재사용 비용이 거의 0. 게다가 CAS번호("64-17-5")나 정확한 화학물질명은 의미 검색만으로는 놓치기 쉬운 정확매칭 케이스라 BM25가 필수 보완재.
- **도입하면 좋은 점**: "이 물질과 반응하는 것" 같은 의미적 질의와 "64-17-5" 같은 정확 코드 질의를 동시에 커버. 신규 개발 없이 기존 코드 재사용 가능.
- **예상 단점**: BM25 인덱스와 dense 인덱스 두 개를 동시에 유지·동기화해야 하는 운영 복잡도.
- **단점 극복 방안**: 적재검증 단계에서 두 인덱스의 문서 수 일치 여부를 자동 체크하는 스크립트를 Stage4 산출물에 포함(별도 운영 작업 아닌 파이프라인 내 검증 단계로 흡수).

### 1.4 FAISS 벡터스토어
- **출처**: dl-pkw.tistory.com/entry/FAISS와-Chroma-벡터-DB-이해하기 (2025-06-20)
- **무엇을 도입했나**: 대용량 로컬 처리에는 FAISS, 메타데이터 필터링에는 Chroma가 유리하다는 비교 결론 중 FAISS 채택.
- **왜 도입했나**: 200종 규모(청크 수 예상 수천 건)는 로컬 처리로 충분하고, KDIC 프로젝트에서 이미 FAISS를 써봤기 때문에 재사용 원칙에 부합. Chroma로 전환할 만큼 메타데이터 필터링 요구가 복잡하지 않음(현재 필터는 CAS/그룹/근거등급 정도).
- **도입하면 좋은 점**: 신규 학습 비용 없음. 로컬 환경(Desktop Commander)에서 바로 실행 가능.
- **예상 단점**: FAISS는 메타데이터 필터링이 Chroma보다 불편함 — 근거등급별 필터링, Abstain 플래그 필터링을 직접 구현해야 함.
- **단점 극복 방안**: FAISS 인덱스와 별도로 SQLite(`reactivity_reference.db`)에 청크ID↔메타데이터 매핑 테이블을 두고, 검색 후 SQLite에서 메타데이터 필터링하는 2단계 구조로 보완(신규 DB 도입 없이 기존 SQLite 자산 재사용).

### 1.5 RAGAS 평가 프레임워크
- **출처**: storycompiler.tistory.com/345 (2026-03-27)
- **무엇을 도입했나**: Faithfulness(충실도), Answer Relevancy(관련성) 등 정답지 없이 진단 가능한 RAG 평가 지표.
- **왜 도입했나**: Stage5(평가) 단계뿐 아니라, 프로젝트 비협상 원칙인 Abstain 정책·근거등급제가 실제로 작동하는지 정량 검증할 수단이 필요했음. "근거 불충분 시 억지로 답하지 않는다"는 원칙은 Faithfulness 지표로 직접 검증 가능.
- **도입하면 좋은 점**: 정답 데이터셋을 별도로 구축하지 않아도 시스템 약점을 진단할 수 있어 MVP 단계에 적합. 오픈소스라 재사용 자산과 마찬가지로 도입 비용 낮음.
- **예상 단점**: RAGAS 내부적으로 LLM을 판정자로 쓰는 지표가 있어, 평가 자체에 API 비용과 변동성(같은 입력도 판정이 다를 수 있음)이 발생.
- **단점 극복 방안**: 전수 평가 대신 200종 중 대표 샘플(그룹별 1~2종, 총 20~30건) 스팟체크로 한정. 판정 변동성은 동일 샘플 2회 이상 평가해 편차 확인 후 최종 채택.

## 2. 제외 (컷) 항목 (3건)

### 2.1 PyMuPDF-Layout
- **출처**: epapyrus.tistory.com/448 (2025-12-12)
- **컷 사유**: PDF 레이아웃(폰트/좌표/GNN 기반 표 인식) 파싱 도구. 우리 수집물은 PDF가 아니라 API의 EAV JSON — 애초에 파싱 대상이 존재하지 않음.
- **트레이드오프**: 향후 KOSHA가 제공하지 않는 원본 MSDS PDF를 별도로 확보해 보강하는 시나리오가 생기면 재검토 대상. 현재 MVP 스코프에서는 불필요.

### 2.2 PDF Loader 비교 (PyMuPDF vs PDFPlumber)
- **출처**: velog.io/@mo_ongh (원 링크는 프로필 목록 페이지로 부정확 — 실제 글은 `/@mo_ongh/PDF-Loader-비교-분석-...`)
- **컷 사유**: 2.1과 동일 — PDF 비교자료이므로 EAV 데이터 구조에는 적용 대상 아님.
- **트레이드오프**: 없음(적용 대상 자체가 없으므로 컷에 따른 손실 없음).

### 2.3 Adaptive Chunking (ekimetrics)
- **출처**: github.com/ekimetrics/adaptive-chunking (LREC 2026 accepted, 실제 존재 확인됨)
- **컷 사유**: 비정형 문서에서 최적 청킹 방식을 동적으로 선택하는 도구. 우리 데이터는 EAV 계층으로 이미 구조화돼 있어 "어떤 청킹이 최적인지 자동 탐색"할 필요 자체가 없음 — 오버엔지니어링.
- **트레이드오프**: 도구 자체는 실존하고 성능도 검증된 것으로 보이나(LREC accepted), MVP 스코프·비용 대비 효율 원칙에 안 맞음. 향후 Stage4 완주 후 검색 성능이 기대에 못 미치고 원인이 청킹 방식으로 특정될 경우 재검토 후보로만 기록.

## 3. 보류 항목 (2건) — MVP 미채택, A/B 비교 후보로만 기록

### 3.1 BGE-m3-ko / 3.2 KURE
- **출처**: huggingface.co/dragonkue/BGE-m3-ko, koreascience.kr/article/CFKO202533761230731
- **보류 사유**: 둘 다 한국어 특화 임베딩 모델로 실존·성능 근거는 확인됐으나, "기존 자산 재사용 우선" 원칙과 정면 충돌. 현재 bge-m3(다국어)로 파이프라인을 끝까지 완주하는 것이 우선.
- **재검토 조건**: RAGAS 베이스라인(bge-m3 기준) 확보 후, 화학/법령 용어 검색에서 Recall이 기대치 이하로 나올 경우에만 BGE-m3-ko 또는 KURE로 교체 A/B 테스트 진행. 지금 시점에 성급히 교체하지 않는다.

> **v2 주석**: 이 "성급히 교체하지 않는다" 판단이 v2에서 뒤집힘 — v2는 처음부터 bge-m3/bge-m3-ko/KURE 3파전 A/B로 진행.

## 4. 최종 파이프라인 순서 (v1, 폐기됨 — v2 참조)

```
분류(Stage2 산출물 재사용)
  → 본문추출 (EAV lev/ordrIdx → 마크다운 헤더 재조립)
  → 청킹 (1차: EAV 항목 경계 / 2차: 600~1200자 + 오버랩 10~25%, 상한 초과 시만)
  → 임베딩 (bge-m3 재사용)
  → 적재+검증 (FAISS+BM25 하이브리드, SQLite 메타데이터 매핑, RAGAS 스팟체크)
```
