## 1. D4 — 검색공간 축소 (§6 payload section 필터 적용)

설계 §6은 vector payload에 `section` 필드를 "검색 시 즉시 필터링" 용도로 넣어뒀으나
구현에서 쓰이지 않고 있었다. 반응성 판정 질의는 §2(유해성·위험성 분류)와
§10(안정성 및 반응성)만 참조하면 되므로 검색 대상을 **805청크 → 409청크**로 좁혔다.

### 적용 근거가 된 오류 분석 (필터 적용 전, dense top-5 오답 727건)

| 항목 | 실측 |
|---|---|
| 오답 중 **질의에 등장한 그 두 물질의 다른 섹션** | 275건 (37.8%) |
| 오답 섹션 분포 | §10 401 / §3 **204** / §9 **71** / §2 51 |
| top-5에서 놓친 정답의 섹션 | §2 303 / §10 109 |

→ 검색기가 물질을 못 찾는 게 아니라, **§3(구성성분)·§9(물리화학) 청크가 정답 자리를
빼앗고** 있었다. MRR 0.9661이 이를 뒷받침한다(1순위는 거의 항상 정답).

### 실측 결과 (dense 기준)

| 지표 | 필터 없음 (805청크) | §2·§10 필터 (409청크) | 변화 |
|---|---|---|---|
| **Recall@10** | 0.8691 | **0.8829** | **+1.59%** |
| Recall@5 | 0.7376 | 0.7804 | +5.80% |
| Recall@20 | 0.9252 | 0.9304 | +0.56% |
| Hit@5 | 1.0000 | 1.0000 | 유지 |
| Hit@10 | 1.0000 | 1.0000 | 유지 |
| MRR | 0.9661 | 0.9837 | +1.82% |
| nDCG@10 | 0.8461 | 0.8772 | +3.68% |
| **검색 지연** | 0.293ms | **0.089ms** | **3.3배 단축** |

**정확도와 속도가 동시에 개선된 순수 이득.** 추가 임베딩 비용 0(문서 벡터 캐시를
자르기만 함).

## 2. 레이턴시 실측 — 기록 정정

### 정정 대상
초기 보고에서 "dense 0.03ms vs hybrid 18.7ms, 624배 단축"이라 적었다. **이 수치를
그대로 아카이빙하면 §12 예산을 잘못 잡는다.** 두 가지가 틀렸다.

1. **배치 평균이었다.** 369개 질의를 한 번에 FAISS로 검색한 총시간 ÷ 369.
   실사용은 질의 1건씩 들어온다. 질의 단위 중앙값으로 다시 재면 dense 0.089ms,
   hybrid 6.281ms(§2·§10 필터 기준).
2. **검색 단계만이었다.** 사용자 응답까지는 **질의문을 벡터로 만드는 시간**이 앞에 붙는다.

### 실제 Retrieval 지연 구성 (§2·§10 필터, 질의 1건 중앙값)

| 구간 | dense | bm25 | hybrid |
|---|---|---|---|
| 질의 임베딩 | 501.724ms | 0ms (불필요) | 501.724ms |
| 검색 | 0.089ms | 6.192ms | 6.281ms |
| **합계** | **501.81ms** | 6.19ms | **508.00ms** |

**전체 지연의 99.98%가 질의 임베딩이다.** bge-m3-ko는 XLM-R large 계열(568M)이고
CPU에서 배치 1로 돌리므로 병목이 여기 걸린다. 검색 엔진 선택은 지연에 거의 영향이 없다.

### §12 목표 대비
- 목표 Retrieval < 500ms → 실측 **501.81ms**. 사실상 경계선.
- 개선하려면 검색이 아니라 **질의 인코더**를 손대야 한다(ONNX Runtime, 양자화,
  또는 더 작은 질의 전용 인코더). 현재 미착수.

## 3. D2 — 청킹 item 단위 폐기

설계 §3("Section Chunk")과 §8("1차 경계: EAV 항목")이 다르게 읽혀 두 단위를 모두
생성했다(section 805청크 / item 7,420청크). 쌍 과제로 전환하면서 item을 폐기했다.

**폐기 사유 — 비교 자체가 성립하지 않음**

쌍당 정답이 section은 4청크, item은 26청크다(§2 항목 9개 + §10 항목 4개, 두 물질).
top-20까지만 검색하므로 item은 원리적 상한이 막힌다.

| | section (정답 4) | item (정답 26) |
|---|---|---|
| Recall@5 상한 | 1.00 | 0.19 |
| Recall@10 상한 | 1.00 | 0.38 |
| Recall@20 상한 | 1.00 | 0.77 |

낮게 나와도 "검색이 나쁘다"가 아니라 **지표 착시**다. 79분을 써서 해석 불가능한 숫자를
얻게 된다.

**부차 사유 2가지**
- 근거 분산: 아세톤 §10에서 `J08 피해야 할 물질`은 "자료없음" 한 줄인데, 정작 판단
  근거인 "격렬하게 중합반응하여 화재와 폭발"은 옆 항목 `J02`에 있다. 쪼개면 흩어진다.
- 노이즈: item 청크 7,420개 중 **2,620개(35.3%)**가 "자료없음" 한 줄짜리.

**보존**: item 청크와 마크다운은 DB에 그대로 둔다(`rag_chunks.granularity='item'`).
LLM 컨텍스트 축소나 정밀 사실조회가 필요해지면 재사용.

## 4. D3 — 평가셋 전면 교체

**폐기된 설계**: "아세톤의 인화점은 몇 도인가?" 형태의 단일물질 사실조회 407건.

**폐기 사유**: 이 시스템의 과제가 아니다. 목표 스코프는 사용자가 물질 **2종 이상**을
입력하고 그것들을 함께 취급할 때의 위험성·유의사항을 받는 것이다. MSDS를 그냥 읽으면
나오는 값을 되묻는 평가셋으로는 제품 성능을 알 수 없다.

**교체된 설계**: 물질 **쌍(2종)** 369건 (Incompatible 135 / Caution 114 / Compatible 120,
CAMEO 판정 카테고리 균형표집). 전체 조합 19,503쌍에서 추출. **쌍은 N종 스코프의 최소
단위 검증**이다 — 3종 이상 입력은 가능한 모든 쌍을 판정해 worst-case(Incompatible >
Caution > Compatible)로 종합하는 방식으로 확장 예정. 이 aggregation 패턴은 이미
`03_compatibility/compatibility_engine.py`가 "다중 그룹에 속한 물질 하나"를 판정할 때
그룹조합 전수평가 후 worst-case로 종합하는 로직으로 구현돼 있다 — 같은 패턴을 물질
조합 레벨로 한 단계 확장하면 된다. **이번 세션에서 실측한 것은 쌍(2종) 단위뿐이며,
N종 종합 로직·평가는 아직 구현·검증되지 않았다.**

정답(gold) = 고정 스키마. 쌍 (A,B)에 대해 A의 §10, A의 §2, B의 §10, B의 §2.
§9(물리화학)는 화재·폭발 위험 정량화에는 쓰이나 "두 물질이 반응하는가"의 1차 근거가
아니므로 제외. §3(구성성분)도 제외.

**비협상 원칙 1과의 관계**: CAMEO 양립성 매트릭스 판정값은 검색 정답에 넣지 않았다.
매트릭스는 SQLite에서 결정론적으로 조회되는 **별도 신호**이고, 위 MSDS 근거로
교차검증되어야 하는 대상이다. 레코드에 `matrix_verdict`로 참고 저장만 한다.

**Abstain 평가셋 81쌍**: 양쪽 물질 모두 §10 "피해야 할 물질"이 자료없음인 쌍.
물질 특정 근거 없이 그룹 근거만 남으므로, 매트릭스 단독판정 금지 원칙에 의해 Abstain 대상.

**보존**: 단일물질 평가셋은 `--task fact`(검색기 부품 점검용)로 남겼다.

## 5. D5 — Hybrid Search 폐기 (실측과 충돌하는 결정)

**결정**: 하이브리드 폐기, dense 단독 채택 (2026-08-06 사용자 지시).
**제시된 사유**: 레이턴시.

### 실측이 이 사유를 지지하지 않는다

| 지표 (§2·§10 필터) | dense | hybrid | 우세 |
|---|---|---|---|
| **Recall@10 (핵심 KPI)** | 0.8829 | **0.9005** | hybrid **+2.0%** |
| Recall@5 | 0.7804 | 0.7811 | 동률 |
| Recall@20 | 0.9304 | **0.9409** | hybrid |
| Hit@5 / Hit@10 | 1.0000 | 1.0000 | 동률 |
| MRR | 0.9837 | **0.9986** | hybrid |
| nDCG@10 | 0.8772 | **0.8932** | hybrid |
| **총 Retrieval 지연** | **501.81ms** | 508.00ms | dense **6.19ms(1.2%)** |

즉 **핵심 KPI로 지정된 Recall@10에서 hybrid가 앞서고, 대가는 전체 지연의 1.2%다.**

### 왜 판단이 뒤집혔나 — 필터가 BM25를 살렸다

필터 적용 **전**에는 hybrid가 열세였고, 그래서 폐기 논의가 시작됐다.

| BM25 단독 | 필터 없음 | §2·§10 필터 | 변화 |
|---|---|---|---|
| Recall@5 | 0.5742 | 0.6757 | **+17.7%** |
| Recall@10 | 0.7393 | 0.7366 | -0.4% |
| MRR | 0.7306 | **0.9796** | **+34.1%** |
| nDCG@10 | 0.6412 | 0.7823 | +22.0% |

검색공간이 §2·§10으로 좁혀지자 BM25의 오답이 크게 줄었고(MRR 0.73 → 0.98),
그 결과 RRF 융합이 dense를 끌어올리는 쪽으로 바뀌었다.

**즉 D5 결정은 D4 적용 전 데이터에 근거한 것이다.** 두 변경이 같은 세션에서 연달아
일어나면서 근거 데이터가 갱신됐다.

### 현 상태 (당시)
사용자 지시대로 **dense 단독을 채택**하고 이 문서에 충돌 사실을 기록한다.
재검토가 필요하면 코드는 보존되어 있어 `retriever=hybrid` 행이 그대로 재현된다.

## 5-1. D5 철회 — Hybrid로 재채택 (같은 날 후속 결정)

**결정**: 위 §5의 실측 충돌 기록을 근거로 dense 단독 결정을 철회하고 **hybrid를
재채택**한다.

**재검토 사유**: §5에서 이미 확인된 대로 §2·§10 필터 적용 후 hybrid가 7개 목표 중
6개(dense는 4개)를 충족하고, 폐기 사유였던 레이턴시 차이(6.19ms)도 사용자가 직접
정한 `Retrieval ≤ 10ms` 예산 안에 들어온다. dense를 유지할 근거가 남아있지 않다고
판단해 재검토 요청을 받아 전환.

**코드 변경**: `04_rag_agent/run_ab.py`의 `evaluate_reranker()`가 D5(1차 결정) 당시
하이브리드 후보를 dense 결과로 바꿔치기하던 `h = d` 우회를 되돌려, 실제 hybrid RRF
순위(`h`)를 리랭커 입력으로 사용하도록 수정. `evaluate()`(embedding 단계)는 애초부터
dense/bm25/hybrid 세 방식을 전부 실측·출력하고 있었으므로 변경 없음 — 이번에
바뀐 것은 "어느 행을 확정값으로 채택하는가"와 리랭커 단계로 넘길 후보뿐이다.

**아직 안 된 것**: 리랭커(§8, D7)는 여전히 미실행 상태다. 리랭커를 실행할 때는 이제
hybrid 후보가 입력으로 들어가므로, D7에서 참조한 Hit@5=1.0000·MRR 0.9837 등의 근거는
dense 기준 수치였다는 점을 감안해 재확인이 필요하다.

**기록의 의미**: D5는 실측과 충돌하는 결정임을 처음부터 숨기지 않고 남겼고(§5), 그
기록이 있었기 때문에 같은 날 안에 재검토·철회가 가능했다. 문서를 "정답만 남기는
방식"이 아니라 "판단이 바뀐 과정 자체를 남기는 방식"으로 쓴 것이 실제로 결정 품질
개선에 쓰인 사례.

최종 확정 구성은 `docs/HANDOFF.md` §0, 전체 의사결정 이력은 `docs/decisions.md` §2.4 참고.

## 6. D1 — 임베딩·리랭커 A/B 폐기

**결정**: 임베딩 = bge-m3-ko, 리랭커 = bge-reranker-base. **A/B 없이 지정.**
설계 §1("모든 핵심 기술은 A/B 테스트 실측으로 결정한다")과 §13 1~2단계를 대체.

**사유**: 무거운 모델 배제 + CPU 전용 환경의 실행시간.

| 실측 근거 | 값 |
|---|---|
| section 청크 임베딩 (4스레드) | 3.80초/청크 → 805청크 51분 |
| section 청크 임베딩 (**8스레드**) | **2.61초/청크 → 35분** |
| item 청크 임베딩 (8스레드, 배치8) | 0.637초/청크 → 7,420청크 79분 |
| item 청크 임베딩 (8스레드, **배치32**) | 1.203초/청크 → **149분** (배치 키우면 2배 느림) |
| 3파전 전체 예상 | **약 5.7시간** |

> **주의**: bge-m3-ko와 bge-reranker-base는 **"A/B 승자"가 아니라 "사용자 지정"이다.**
> KURE, bge-reranker-v2-m3와의 비교 실측은 존재하지 않는다. 성능 우위 주장 금지.

**설계 문서 사실오류 발견**: §5는 `bge-reranker-v2-m3`를 "경량/빠름",
`bge-reranker-base`를 "대형/고성능"이라 적었으나 **반대**다.
실제 v2-m3 = 2.2GB(568M), base = 1.2GB(278M). 문서 수정 대기.

## 7. D6 — KPI 재설계 / §11 목표치 재조정 제안

**확정**: 핵심 KPI = **Recall@10**. 현업 지표(Recall@10, MRR, Hit@5/10, Latency)를 따름.
`Hit@k`(top-k에 정답이 하나라도 있으면 1) 지표를 새로 구현해 추가.

### §11 목표치 재조정 — **확정 (2026-08-06 사용자 지정, 현업 기준)**

설계 §11/§12를 대체한다. 레이턴시는 **구간별로 분리**한다 — 질의 임베딩과 검색은
병목 성격이 완전히 달라서 하나의 예산으로 묶으면 어느 쪽을 손봐야 하는지 알 수 없다.

| 구간 | 지표 | 확정 목표 | 실측 dense | 판정 | 실측 hybrid | 판정 |
|---|---|---:|---:|:--:|---:|:--:|
| 정확도 | **Recall@10** (핵심) | **≥ 0.89** | 0.8829 | **미달** | 0.9005 | 충족 |
| | MRR | **≥ 0.98** | 0.9837 | 충족 | 0.9986 | 충족 |
| | nDCG@10 | **≥ 0.88** | 0.8772 | **미달** | 0.8932 | 충족 |
| | Hit@5 | **1.00 유지** | 1.0000 | 충족 | 1.0000 | 충족 |
| 지연 | Embedding | **≤ 500ms** | 501.724 | **미달** | 501.724 | **미달** |
| | Retrieval(검색) | **≤ 10ms** | 0.089 | 충족 | 6.281 | 충족 |
| | Total (TTFT 전) | **≤ 600ms** | 501.81 | 충족 | 508.00 | 충족 |

**충족 현황: dense 4/7, hybrid 6/7.**

- Recall@5는 참고치로 강등(정답 4.1개를 5칸에 담아야 하는 구조. §11의 k값은 정답 1개 전제).
- `Embedding ≤ 500ms`는 dense·hybrid 공통으로 **1.724ms(0.34%) 초과**. 사실상 경계선이며
  검색 방식과 무관하다. 여유를 만들려면 질의 인코더를 손대야 한다(§2, §11-3).
- `Retrieval ≤ 10ms` 예산은 hybrid의 6.281ms를 **수용한다**(여유 37%).
  dense의 0.089ms는 예산 대비 112배 여유로, 이 구간에서 더 아낄 실익이 없다.

> **기록**: 이 확정 KPI를 실측에 대입하면 §5에서 폐기된 hybrid가 dense보다
> 2개 지표(Recall@10, nDCG@10)를 더 충족한다. 폐기 사유였던 레이턴시는
> 사용자가 직접 정한 `Retrieval ≤ 10ms` 예산 안에 들어온다.
> 결정은 dense 유지(사용자 지시). 이 충돌 사실을 근거와 함께 남긴다.

## 8. D7 — 리랭커 미실행

**결정**: 리랭커 불필요 (사용자 판단).

**뒷받침하는 실측**:
- Hit@5 = Hit@10 = **1.0000**. 모든 질의에서 top-5 안에 정답이 최소 1개.
  리랭커가 해결할 "정답이 아예 안 잡히는" 문제가 없다.
- MRR 0.9837 — 1순위가 거의 항상 정답. 재정렬 여지가 작다.
- 비용: bge-reranker-base 실측 1.09초/쌍 × 369질의 × 20후보 = **최대 134분**,
  그리고 §12 TTFT 예산을 직접 잠식한다.

**남은 문제는 순위(Recall)이지 탐지(Hit)가 아니다.** 리랭커는 후보 안에서 순서를
바꾸는 도구이므로 Recall@10 개선에 기여할 여지는 있으나, 134분과 지연 증가 대비
기대 이득이 불확실해 미실행.

## 11. 확장성 벤치마크 계획 (스켈레톤 — 미실행)

현재 실측은 **198종 / 805청크** 기준이다. 실서비스에서 500종·1,000종으로 늘어날 때
FAISS를 유지할지 Qdrant로 전환할지(설계 §7의 미결 항목) 판단할 근거를 지금 확보해 둔다.
**계획만 기록하며, 실행은 확장이 실제로 결정된 뒤에 한다.**

### 11.1 측정 지점

청크/물질 환산비: 현재 198종 → 805청크(전체) / 409청크(§2·§10 필터) = **약 4.07청크/종**

| 지점 | 청크 수(전체) | 환산 물질 수 | 성격 |
|---|---:|---:|---|
| P0 | 805 | 198 | **현재 실측 완료** (기준선) |
| P1 | 약 2,030 | 500 | 1차 확장 시나리오 |
| P2 | 5,000 | 약 1,230 | 사용자 지정 측정점 |
| P3 | 10,000 | 약 2,460 | 사용자 지정 측정점 |

### 11.2 측정 항목

| 항목 | 왜 재는가 | P0 실측 |
|---|---|---|
| 검색 지연 (질의 1건 중앙값) | `Retrieval ≤ 10ms` 예산 소진 시점 | dense 0.089ms(409청크) / 0.293ms(805청크) |
| 질의 임베딩 지연 | **청크 수와 무관한 상수**. 대조군 | 501.724ms |
| Recall@10 / MRR / nDCG@10 / Hit@5 | 코퍼스가 커지면 오답 후보가 늘어 하락하는지 | 0.8829 / 0.9837 / 0.8772 / 1.0000 |
| 인덱스 빌드 시간 | 운영 중 재색인 부담 | (미측정) |
| 메모리 상주량 | 1024차원 float32 = 청크당 4KB. 10,000청크 = 약 41MB | (미측정) |
| **문서 임베딩 총비용** | 실제 확장 병목 | 2.61초/청크 → 10,000청크 = **약 7.2시간(CPU)** |

### 11.3 예상과 검증 대상

- `IndexFlatIP`는 완전탐색이라 검색 지연이 청크 수에 **선형**이다.
  P0에서 805청크 0.293ms → 10,000청크 선형 외삽 시 **약 3.6ms**로,
  `Retrieval ≤ 10ms` 예산 안에 들어온다.
  → **가설: 10,000청크까지는 FAISS IndexFlatIP로 충분하다.** 이 가설을 검증하는 것이
  이 벤치마크의 1차 목적이다.
- 선형성 자체를 확인해야 한다. P0의 409→805청크 구간에서 0.089→0.293ms로
  청크 2배에 시간 3.3배가 나왔는데, 이 규모에서는 측정 잡음일 가능성이 크다.
  P1~P3에서 실제 기울기를 봐야 한다.

### 11.4 코퍼스 확보 방법과 그 한계

실제 MSDS 추가 수집은 KOSHA API 호출 비용이 든다(물질당 5콜). 확장성 측정만이 목적이라면
기존 청크를 변형 복제해 코퍼스를 부풀리는 방법이 있다(물질명·CAS 치환).

> **한계를 명시한다**: 합성 코퍼스에서 **지연·메모리·빌드시간은 유효**하지만
> **Recall 계열은 의미가 제한적**이다. 복제된 청크는 실제 물질처럼 서로를 헷갈리게
> 만들지 않기 때문이다. Recall 변화는 **실데이터 확장 시점에 재측정**해야 한다.

### 11.5 Qdrant 전환 판단 트리거

아래 중 하나라도 관측되면 설계 §7의 Qdrant 검토를 재개한다. 그 전에는 FAISS 유지.

1. 검색 지연이 `Retrieval ≤ 10ms` 예산을 초과
2. 메타데이터 필터가 복잡해져 현재 방식(Python에서 벡터 배열을 잘라 쓰는 §1의 D4 구현)으로
   감당이 안 될 때 — 예: 근거등급·CAMEO 그룹·개정일 다중조건 동시 필터
3. 인덱스 재빌드 시간이 운영 주기를 넘어설 때
4. 다중 프로세스에서 인덱스를 공유해야 할 때(FAISS 인메모리 구조의 한계)

### 11.6 기록의 목적

이 계획을 남기는 이유는 나중에 **"왜 FAISS를 유지했는가"** 또는 **"왜 Qdrant로 갔는가"**를
실측 근거로 답하기 위해서다. 설계 §7은 현시점 재검토 트리거가 없다고만 적혀 있는데,
그 "트리거"를 위 11.5로 구체화한다.
