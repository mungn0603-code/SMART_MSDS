### KOSHA 403 해결, 200종 수집

- **403의 원인을 확정했다.** 서비스키가 마이페이지에서는 승인완료 상태인데도 모든

  인코딩 3가지를 바꿔 보고, data.go.kr 공식 테스트 화면에서도 같은 실패를 재현해
  **우리 코드 문제가 아니라 포털 쪽 계정-키 연동 문제**임을 확정했다. 사용자가 KOSHA에
  직접 문의해 조치를 받은 뒤 같은 키로 정상 응답을 확인했다.
- **1차 수집**: 200종의 §2/§3/§9/§10을 시도해 **168종 성공**(6,720행), 32종 미발견.

  채우려고 자동 보충한 물질(군용폭약·단종농약 등 KOSHA 미등록 희귀물질)이었다.

    발암물질)·블레오미신(항암제)·안트랄린(치료제) 등 10건이 부적절했다.
  - 2라운드(GHS 위험문구 + KOSHA 권고용도 자동 필터 추가): 다시 골랐는데 **아플라톡신

### RAG 검색 계층 설계·구현·측정

- **설계를 v1에서 v2로 전면 교체했다.** v1의 최상위 원칙("기존 자산 재사용 우선")을
  버리고 v2("검색 성능 우선")로 바꿨다. v1은 `archive/design_docs/`에 보존했다.
- 청킹 파이프라인(`pipeline.py`)을 만들어 section 청크 805개, item 청크 7,420개를
  생성했다.
- 검색 계층(`retrieval.py`)을 만들었다: bge-m3-ko 임베딩 + FAISS + BM25(kiwipiepy) +
  RRF 융합 + 리랭커.
- **평가셋을 전면 교체했다.** 제품이 답해야 하는 것은 "물질 2종 이상의 조합"인데
  처음 만든 평가셋은 단일물질 사실조회였다. 그 최소 단위인 **쌍(2종)** 기준으로 다시
  만들었다 — `gold_pair.jsonl` 369쌍(Incompatible 135/Caution 114/Compatible 120),
  `gold_pair_abstain.jsonl` 81쌍. 단일물질 평가셋은 부품 점검용으로 격하했다.
  3종 이상 조합은 "쌍 판정을 모아 가장 위험한 쪽을 택한다"는 설계까지만 하고 구현은
  미뤘다.
- **측정해서 확인한 것**:
  - **§2·§10 섹션만 검색 대상으로 좁히면**(805→409청크) 정확도(Recall@10 +1.59%p,
    nDCG@10 +3.68%p)와 속도(3.3배)가 **동시에** 개선된다.
  - **hybrid와 dense의 충돌**: 같은 조건에서 hybrid가 목표 7개 중 6개, dense가 4개를
    충족했다(Recall@10 hybrid 0.9005 > dense 0.8829). 그럼에도 사용자 지시로 dense를
    채택했다 — 속도 차이(6.19ms)가 정해둔 예산(10ms) 안에 들어왔기 때문이다.
  - 리랭커는 실행하지 않기로 했다(Hit@5=Hit@10=1.0000이라 "못 찾는" 문제가 없다).
- LLM 클라이언트(`llm.py`)를 작성했다(API 키 미설정 상태).
- 저장소를 정리했다. 최종 채택 파일과 실행 로그·기각 파일을 분리해 `archive/`를
  분야별로 나누고, 폴더마다 사유를 적은 `NOTES.md`를 남겼다.
- **검색 방식 결정을 같은 날 되돌렸다.** 문서를 다시 검토하다 "성능이 더 좋은 방법을
  알면서 안 쓰는 상태"라는 지적이 나왔고, 이미 기록된 근거(§2·§10 필터 적용 후 hybrid
  6/7 vs dense 4/7)에 따라 **dense 단독을 철회하고 hybrid로 재채택**했다. 코드의 dense
  우회 부분도 되돌렸다. 리랭커는 여전히 미실행으로 남겼다.

## 2026-08-08 — CAMEO 데이터 소스를 PubChem 공식 경로로 전환

- **경로를 확정했다.** CAS→CID는 공식 PUG-REST, CID→CAMEO 그룹은 PubChem Classification
  Browser의 `hid=86`("CAMEO Chemical Reactivity Classification")이다. 핸드오프 초안이
  가정했던 `hid=80`은 다른 분류 체계라 오답이었다.
- **3,396종 전체를 다시 조회했다.** 일치 3,185 + 표기만 다른 사실상 일치 7 = **94.0%가
  그대로 재검증**됐다. 나머지 6.0%는 진짜 결측 9종(혼합물 표기 등)과 CID 조회 실패
  195종 — 고분자·천연수지·광물처럼 PubChem이 "단일한 분자 구조"를 전제로 색인하는 범주
  밖의 물질이라 원래 잡히지 않는다. 조회 로직의 결함이 아니다.
- **부수 정정**: UREA의 CAS가 `497-19-8`(실제로는 탄산나트륨)로 잘못 등록돼 있었고
  올바른 UREA 레코드가 따로 있어 완전 중복이었다 — 중복을 삭제했다. 그룹 42
  ("Metals, Less Reactive...")와 48("Not Chemically Reactive...")의 이름 표기를 통일해
  가짜 불일치 12종을 해소했다.
- **직접 수집 원본을 아카이브로 옮겼다**(`archive/01_collection/`). DB를 0부터 다시 만들
  때 필요한 시드 CSV 2종만 남기고 시드 스크립트의 경로 상수를 아카이브 경로로 바꿨다.
- **이 시점 이후 `chemical_group_membership`의 행 단위 출처 구성**(참고용 스냅숏, 총
  6,731행): `CAMEO_scrape` 6,658 / `pubchem_cameo_2026-08-22` 48 / `pubchem_verified` 14 /
  `manual_classification_verified` 11. 즉 **저장된 매핑의 다수는 이전 수집분이고 PubChem
  경로가 그것을 검증·보완했다.** 신규 매핑을 확보하는 경로는 위의 PubChem 경로 하나다.
- **환경 이슈**: 전체 재수집과 KOSHA 수집이 동시에 DB에 쓰면서 `database is locked`가
  반복됐다. 수집기의 DB 연결에 대기시간 120초를 주어 해결했다.
