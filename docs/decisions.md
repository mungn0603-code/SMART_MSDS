# 기술/설계 결정 기록 (Decision Log)

이 문서는 프로젝트 전반의 **철학**과 **개별 기술 선택의 근거**를 한곳에 모은다. 각 결정에는
근거 유형을 명시한다 — **실측**(이 프로젝트에서 직접 측정) / **사용자 지정**(실측 없이
결단) / **외부 출처**(문서·논문 인용, 신뢰도 별도 표기) / **구조적 논증**(데이터 구조상
자명함).

세부 실측 수치와 원본 근거는 `docs/HANDOFF.md`, `docs/stage4_design_changes_2026-08-06.md`,
`docs/HANDOFF_ARCHIVE.md`를 참조. 데일리 로그는 `docs/PROJECT_LOG.md`.

## 0. 이 프로젝트의 메타 원칙

### 0.1 "실측 vs 사용자 결단"을 항상 구분해서 기록한다
**결정**: 모든 설계 변경에 대해 근거가 데이터 실측인지, 사용자가 실측과 무관하게 내린
결단인지를 구분해 기록한다. 실측과 최종 결정이 어긋나는 경우에도 결정을 실측 쪽으로
조용히 맞추지 않고, **충돌 사실 자체를 문서에 남긴다**.
- **근거 유형**: 프로젝트 운영 원칙(메타 결정)
- **출처**: 자체 수립
- **실제 적용 사례**: §3.5 (Dense vs Hybrid) — hybrid가 핵심 KPI(Recall@10)를 포함해
  7개 목표 중 6개를 충족했음에도 성능이 더 좋은 dense를 채택했고, section filter 적용 후 hybrid가 더 높은 성능을 기록해 재수정했다. 실측을 왜곡하지 않고 기록해 앞으로의 방향성에 영향을 끼친다.

### 0.2 최상위 우선순위: 검색 성능 > 유지보수성 > 확장성 
**결정**: Stage 4(RAG) 설계 v2에서 확정. "기존에 써봤다"는 사실 자체는 채택 근거가
될 수 없고, 재사용은 성능이 동률일 때만 고려한다.
- **근거 유형**: 사용자 결단(철학 교체)
- **출처**: 자체 수립
- **배경**: 원래 v1은 정반대 철학("(KDIC 프로젝트) 재사용 우선")으로
  출발했으나, 2026-08-06 전면 교체됐다. v1은 폐기하지 않고
  `archive/design_docs/`에 "왜 재사용 우선을 버렸는지 비교 대조용"으로 보존.
  **철학 자체를 뒤집고 그 이유와 이전 버전을 그대로 남긴 것**은 의도적
  선택이었다.

### 0.3 비협상 원칙 4종 (프로젝트 시작부터 불변)
1. 양립성 매트릭스 조회 결과를 **단독** 최종 판정 근거로 사용 금지 — 참고자료일 뿐.
2. CAMEO 최신 68그룹 체계 엄격 적용(구 EPA 41그룹 폐기).
3. 근거 부족 시 **Abstain** — 억지로 답변하지 않는다.
4. 근거 등급제: 법령(Mandatory) > 권고(Recommended) > 참고자료(Reference).
- **근거 유형**: 사용자 결단 / 원 출처는 EPA 매트릭스 원문의 "단독 판정 금지" 경고 계승
- **출처**: EPA-600/2-80-076 원문 경고 문구

## 1. 도메인 / 데이터 결정

### 1.1 CAMEO 68그룹 체계 채택 (구 EPA 41그룹 폐기)
- **결정**: 반응성 분류 체계로 CAMEO의 최신 68그룹을 쓴다.
- **근거**: 41그룹은 CAMEO가 이후 68그룹으로 확장하기 전의 구버전 — 최신 체계를 쓰지
  않을 이유가 없음.
- **근거 유형**: 구조적 논증(더욱 검증된 최신 자료)
- **출처**: CAMEO/EPA 공개 자료

### 1.2 타겟 물질 스코프: 200종 (3,386종 전체 풀 확대안 기각)
- **결정**: 학부 실험실 커버리지 기준 200종 유지. CAS 매핑으로 확보된 3,386종 전체
  풀로의 확대는 미채택.
- **근거**: API quota(개발 계정 기준 1,000콜/일 가정치), MVP 스코프 유지. 3,386종 확대 아직 미채택. 하지만 KOSHA 운영계정 신청 시, 일일 트래픽 100000 사용 가능. 
- **근거 유형**: 사용자 결단(2026-08-04)
- **출처**: 공공데이터포털 물질안전보건자료 조회 서비스
- **트레이드오프**: 200종은 68/68 CAMEO 그룹을 전부 커버하지만, 그룹당 대표성은
  1~수종 수준. 통계적 일반화보다 "그룹 커버리지 완전성"을 우선한 설계.

### 1.3 규칙기반 분류 우선, LLM은 보조
- **결정**: 반응성 그룹 분류는 키워드/정규식 규칙기반을 우선하고 LLM은 보조 수단으로만 쓴다.
- **근거**: LLM 단독 분류 정확도가 90% 문턱에 못 미친다는 근거(84%)를 인용.
- **근거 유형**: 외부 출처 — **세부 수치 미검증**
- **출처**: arXiv:2606.11204 (`docs/msds_risk_assessment_readme.md` §2 인용). **주의**:
  이 논문의 존재·주제 일치 여부와 인용된 84%/90% 수치가 원문 대조로 검증됐다는 기록이
  없다. 포트폴리오에서 이 수치를 인용할 경우 원문을 직접 열람해 재확인 권장.

### 1.4 근거 등급제 판정 규칙 (법령 > 권고 > 참고)
- **결정**: 섹션2(GHS분류·H/P코드, 고용노동부고시 별표 확정문구) → Mandatory. 섹션
  3·9·10 중 `※출처` 미표기(KOSHA 자체 작성값) → Recommended. `※출처` 표기 항목

- **근거 유형**: 구조적 논증(KOSHA 데이터의 출처표기 관행을 그대로 신호로 사용)
- **출처**: KOSHA MSDS 데이터 자체의 표기 관행 근거

## 2. RAG 아키텍처 결정

### 2.1 임베딩 = bge-m3-ko 도입, 리랭커 = bge-reranker-base 적용 보류 — A/B 없이 사용자 지정
- **결정**: 설계 v2가 명시한 "모든 핵심 기술은 A/B 실측으로 결정한다" 원칙을 이 항목만
  예외로 두고, 사용자가 직접 지정.
- **근거**: 무거운 3파전(bge-m3/bge-m3-ko/KURE) A/B에 CPU 전용 환경에서 약 5.7시간이
  소요된다는 실측 추정 → 사용자가 시간 대비 실익이 낮다고 판단해 A/B를 건너뜀.
- **근거 유형**: 사용자 결단(실측 시간 배경)
- **출처**: bge-m3-ko는 `huggingface.co/dragonkue/BGE-m3-ko`, KURE는
  `koreascience.kr/article/CFKO202533761230731` — 두 모델의 실존·개요는 v1 설계
  단계에서 확인됐으나, **이 프로젝트 데이터에서의 성능 비교 실측은 존재하지 않는다**.
  -bge-m3 ko로도 충분한 성능 확인 마침.
  `docs/stage4_design_changes_2026-08-06.md` §6에 "성능 우위 주장 금지"로 명시.

### 2.2 청킹: section 단위 단독 (item 단위 폐기)
- **결정**: EAV 항목(item, 7,420개) 단위 청킹을 버리고 section(805개) 단위만 쓴다.
- **근거**: 물질 쌍 과제에서 쌍당 정답이 section 4개 vs item 26개인데 top-20까지만
  검색하므로 item은 Recall@10 원리적 상한이 0.38로 막힌다 — 낮게 나와도 "검색이
  나쁘다"가 아니라 지표 착시. 부차적으로 item 청크의 35.3%가 "자료없음" 한 줄짜리
  노이즈였고, 판단 근거가 인접 항목에 흩어지는 문제도 확인.
- **근거 유형**: 실측 + 구조적 논증
- **출처**: 자체 실측. item 청크·마크다운은 DB에 보존되어 있어 정밀 사실조회
  용도로 재사용 가능.

### 2.3 검색공간 축소: 섹션 §2·§10 필터 (805→409청크)
- **결정**: 반응성 판정 질의는 §2(유해성분류)·§10(안정성·반응성)만 검색 대상으로 좁힌다.
- **근거**: 필터 적용 전 dense top-5 오답 727건 분석 결과, §3(구성성분)·§9(물리화학)
  청크가 정답 자리를 빼앗고 있었음(오답의 37.8%가 "질의에 등장한 물질의 다른 섹션").
  필터 적용 후 Recall@10 +1.59%p, nDCG@10 +3.68%p, 검색 지연 3.3배 단축 — **정확도와
  속도가 동시에 개선된 순수 이득**.
- **근거 유형**: **실측** (이 프로젝트에서 근거가 가장 강한 결정)
- **출처**: 없음(자체 실측), 상세 수치는 `docs/stage4_design_changes_2026-08-06.md` §1

### 2.4 검색 방식: Hybrid 재채택 (Dense 단독 결정 철회)
**현재 상태(최신)**: **Hybrid(dense+BM25 RRF) 채택.** 
§0.1 원칙에 따라 순서대로 남긴다.

1. **1차 결정(2026-08-06, §2.3 필터 적용 전)**: FAISS dense 검색만 쓰고 BM25+dense
   RRF 하이브리드는 폐기. 제시된 사유는 레이턴시.
2. **충돌 발견**: §2.3(섹션 §2·§10 필터) 적용 **후** 재실측하니 같은 조건에서 hybrid가
   Recall@10 0.9005(dense 0.8829보다 +2.0%p), nDCG@10·MRR도 hybrid 우세. 레이턴시
   차이는 6.19ms로 사용자가 직접 정한 예산(Retrieval ≤ 10ms) 안에 들어옴. **7개 목표
   중 hybrid 6개 충족, dense는 4개.** 원인은 1차 결정이 §2.3 필터 적용 **이전** 데이터
   (당시 hybrid 열세)에 근거했기 때문 — 필터 적용으로 BM25 성능이 크게 개선(MRR
   0.73→0.98)되며 근거 데이터가 갱신됐는데 결정은 따라가지 못한 것.
3. **재검토 후 철회 및 재채택(현재)**: 필터 적용 후 실측이 일관되게 hybrid 우세를
   가리키고, 레이턴시 사유도 예산 안에 들어온다는 점이 이미 §2.3 단계에서 확인돼
   있었으므로 dense 단독 결정을 철회하고 hybrid로 전환. 코드 변경:
   `04_rag_agent/run_ab.py`의 `evaluate_reranker()`가 하이브리드 후보를 dense로
   바꿔치기하던 부분(`h = d` 우회, 1차 결정의 흔적)을 되돌려 실제 hybrid 순위(`h`)를
   리랭커 입력으로 쓰도록 수정.
- **근거 유형**: 실측(1차 결정만 사용자 결단, 재채택은 실측 근거로 복귀)
- **출처**: 없음

### 2.5 평가 과제 재정의: 단일물질 사실조회 → 물질 쌍 (목표 스코프의 최소 단위)
- **결정**: 초기 평가셋(단일물질 사실조회 407건, 예: "아세톤의 인화점은?")을 버리고
  물질 쌍 369건(Incompatible 135/Caution 114/Compatible 120)으로 교체.
- **근거**: 제품이 실제로 받는 입력은 **2종 이상 다중 물질**이지, 단일 물질 사실조회가
  아니다 — MSDS를 그냥 읽으면 나오는 값을 되묻는 평가셋으로는 제품 성능을 검증할 수
  없다는 설계 오류를 뒤늦게 인지.
- **스코프 정확화**: "쌍(2종)"은 다중 물질 스코프 **그 자체가 아니라 최소 단위**다.
  N종(N≥3) 조합 판정 로직은 §2.10에서 이 쌍 판정을 재사용해 구현됨. 단, RAG 검색
  계층 실측(§2.3, §2.4)은 여전히 쌍(2종) 질의 기준뿐이라는 점은 구분할 것 — §2.10 참고.
- **근거 유형**: 설계 오류 정정
- **출처**: 없음
- **보존**: 단일물질 평가셋은 검색기 부품 점검용(`--task fact`)으로 남겨둠 — 버리지
  않고 용도를 재정의.

### 2.10 다중 물질(N≥2) 판정: 쌍 전수분해 + 3계층 리포트 — **구현 완료 (2026-08-07)**

#### 문제 재정의
실험실에서 실제로 쓰는 물질은 흔히 3종 이상이다. 처음 설계(위쪽 초안)는 "N종 전체를
worst-case 한 마디로 요약"이었는데, 실사용자가 원한 건 그게 아니었다 — **① 입력한
물질 각각이 뭔지 간단한 프로필, ② 물질끼리 매핑됐을 때 어떤 반응이 나는지 전부,
③ 그 반응들의 유의사항을 쌍별로 따로 볼 수 있어야 한다.** 하나의 점수로 뭉개면
"셋 중 뭐가 문제인지"가 안 보인다. 그래서 worst-case 요약은 "빠른 결론" 용도로만
남기고, 실제 주력 출력은 **전부 보여주는 쪽**으로 다시 짰다.

#### 왜 N종 전용 데이터를 새로 안 만들었나
CAMEO 원자료 자체가 그룹×그룹 **쌍** 매트릭스(68×68)다. N종 전용 반응성 표는
어디에도 없다. 만들려면 그룹 3개 조합만 68C3 = 50,116가지 — 실측도, 출처도 없는
값을 새로 채워 넣어야 한다. 이건 **원칙 1(근거 없는 판정 금지)**·**원칙 3
(근거 부족시 Abstain)** 정면 위반이다. 그래서 N종 데이터를 새로 만드는 방향은
애초에 검토 대상에서 제외.

#### 채택한 방식: 쌍 전수분해 + worst-case + 3계층 리포트
1. **분해**: 입력 N종을 중복 제거한 뒤, 가능한 모든 쌍 C(N,2)로 쪼갠다
   (`itertools.combinations`). 3종이면 3쌍, 5종이면 10쌍.
2. **판정 재사용**: 쌍 하나하나는 기존 §2.5의 `judge_pair_by_cas(cas_a, cas_b)`를
   **그대로** 호출한다 — 새 판정 로직을 만들지 않았다. Abstain 처리, 근거등급
   (Reference 고정), 면책고지, "그룹 여러 개 소속시 그룹조합 전수평가 후
   worst-case" 로직까지 전부 기존 함수에서 상속된다. 이유: 물질 하나가 그룹 여러
   개에 속할 때 "그룹조합을 전수평가해 worst-case로 합친다"는 패턴이 이미
   `judge_pair_by_cas` 안에 있었다(그룹 레벨). 물질 N개를 물질쌍으로 전수평가하는
   건 그 패턴을 물질 레벨로 한 단계 그대로 올린 것뿐 — 새 개념이 아니다.
3. **결과를 하나로 뭉개지 않고 3계층으로 분리**:
   - **`SubstanceProfile`** (물질별 프로필): CAS, 이름, 소속 CAMEO 그룹. "이 물질이
     뭔지"만 보여준다. `chemicals`/`chemical_group_membership` 테이블 조회 재사용
     (`resolve_cas_to_groups`, 기존 함수). MSDS 원문 유해성 문구(GHS H/P코드 등)는
     여기서 안 끌어옴 — 그건 04_rag_agent가 다루는 영역이라 스테이지 경계를
     넘지 않기로 함(과설계 방지). 필요해지면 그때 그 계층과 연결.
   - **`to_table()`** (전체 매트릭스): N×N 마크다운 표, 칸 값은 category
     문자열 그대로(Compatible/Caution/Incompatible/Abstain). 색만 입히면 히트맵
     완성 — 프론트 없는 지금 단계에서는 실제 렌더링(matplotlib 등) 없이 이
     데이터 형태까지만 제공(YAGNI, 아래 "안 한 것" 참고).
   - **`pair_reports()`** (쌍별 상세): 쌍마다 독립된 블록으로 사유, 그룹쌍
     유의사항(`compatibility_pairs.description`/`hazard_codes_raw`/`gas_products_raw`),
     그 쌍에 한정된 abstain 경고를 따로 묶는다. UI 카드 하나씩으로 바로 쓸 수 있는
     단위.
   - **`full_report()`**: 위 셋 + 면책고지를 프로필→표→쌍별상세 순서로 이어붙인
     완성 리포트. 세 조각은 독립적으로도 쓸 수 있게 분리 유지(합치기만 하는
     레이어라 삭제해도 나머지는 안 깨짐).
   - **worst-case 단일 category**는 버리지 않고 유지 — "전체적으로 안전한가?"
     한마디가 필요한 소비자(예: 상단 배지 표시)를 위한 요약값으로 남겨둠.
4. **종합 순위**: `_VERDICT_RANK = {Compatible:0, Abstain:1, Caution:2, Incompatible:3}`.
   Abstain을 Compatible보다 위에 두는 이유 — "모른다"가 "확인된 안전"보다 덜
   위험하다고 말할 근거가 없다. 반대로 Incompatible/Caution처럼 **확정된 위험
   신호가 하나라도 있으면 그게 항상 이긴다** — 불확실성(Abstain)이 확정된
  위험 신호를 가리면 안 되기 때문. abstain_notes는 worst-case에 안 뽑혀도
   전부 취합해 살려둔다(침묵 금지 원칙, §0.3).
5. **입력 정리**: 중복 CAS는 자동 제거(`set`). 고유 CAS가 1개 이하로 남으면
   `ValueError` — "조합"이 성립하지 않는 입력이라는 신호.
